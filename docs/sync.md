# Синхронизация с GitHub

`src/sync/` — три файла: `githubClient.ts` (обёртка над Contents API),
`errors.ts` (типизированные ошибки), `syncService.ts` (оркестрация).

**Синхронизация — бэкап, а не зависимость.** Приложение полностью работает без сети и
без токена. Ни одно локальное действие не блокируется и не падает из-за
синхронизации.

## Почему без бэкенда

`api.github.com` отдаёт разрешающий CORS и допускает заголовок `Authorization`,
поэтому PWA вызывает его напрямую с origin GitHub Pages. Своего сервера не нужно.

## Токен

Fine-grained PAT, вводится вручную в настройках, хранится в IndexedDB отдельной
строкой `settings['token']`. В коде и бандле токена нет.

Отдельная строка — чтобы «Удалить токен» был одним `delete` и чтобы ни один путь
кода не мог случайно сериализовать токен вместе с остальными настройками. В UI он
write-only: после сохранения он никогда не читается обратно в состояние компонента,
поэтому не может всплыть в дереве React DevTools, в сериализованной ошибке или на
скриншоте.

Почему такое решение вообще приемлемо: GitHub Pages раздаёт только статику, спрятать
секрет на клиенте невозможно в принципе. Ручной ввод плюс узкий scope (один
репозиторий, `Contents: Read and write`) ограничивают радиус поражения. Если токен
утечёт — теряются записи о чаях, а не аккаунт. В UI это сказано прямо: «токен
хранится в этом браузере, не вводите его на чужом устройстве».

**Никогда не добавляй runtime-кеш, который может совпасть с `api.github.com`** — это
записало бы запрос с токеном в Cache Storage. В `e2e/smoke.mjs` есть проверка, что
кеш пуст в этом отношении.

## Коды ошибок fine-grained PAT

Ведут себя не так, как подсказывает интуиция. `src/sync/errors.ts`:

| Код | Что это на самом деле |
|---|---|
| `404` на `GET /repos/...` | **Не «репозитория нет».** Приватный репозиторий вне списка selected repositories токена отвечает 404, а не 403. Текст ошибки обязан покрывать оба случая — на это есть тест. |
| `404` на `getContent` | Вообще не ошибка: файла ещё нет, надо создать. Клиент возвращает `null`. |
| `403` | Одно из трёх: нет права `Contents: Read and write`; репозиторий не выбран для токена; не авторизован SSO организации. API их не различает, поэтому перечисляются все три. |
| `403` / `429` с `x-ratelimit-remaining: 0` | Лимит запросов. Отличить от проблемы прав можно **только** по заголовку. |
| `409` / `422` | Устаревший `sha`. Лечится перечитыванием и одним повтором. |

Пустой токен **не отправляется** как `Authorization: Bearer ` — GitHub на это
отвечает 401 даже для публичного репозитория, и UI сообщил бы «токен недействителен»
там, где токена просто нет.

## Механика

Все операции сериализуются через мьютекс на цепочке промисов. Параллельные коммиты в
одну ветку гоняются и дают 409, а личному приложению распараллеливать нечего. Есть
тест, что в полёте всегда не больше одного запроса.

### Очередь

Очередь — это `syncMeta.dirty` плюс стор `tombstones`. Отдельного стора очереди нет
намеренно: очередь, выведенная из текущего состояния, идемпотентна по построению —
нет дублей и нет проблем порядка, в отличие от журнала интентов.

Слив очереди: при старте приложения, на событие `online`, и по кнопке.

### Push — порядок действий несущий

1. **Проверка конфликта** (см. ниже).
2. **Картинка первой**, потом markdown — чтобы `image:` никогда не указывал на
   ещё не существующий файл.
3. `PUT` md с сохранённым `sha`.
4. При переименовании: `PUT` нового пути, затем **отдельным запросом** `DELETE`
   старого. Документация API прямо предупреждает не выполнять PUT и DELETE по одному
   репозиторию параллельно.
5. На `409`/`422` — перечитать `sha` и повторить **один раз**.

Между записями пауза 250 мс. Первичный лимит 5000/час недостижим; реальный риск —
вторичный лимит на серии записей.

### Конфликты — спрашиваем, а не перезаписываем

Перед перезаписью проверяем, несёт ли удалённый файл тот `updatedAt`, который мы
туда положили в последний раз (`syncMeta.lastPushedUpdatedAt`). Если нет — писал кто-то
другой, и пользователь выбирает: перезаписать своей, взять из репозитория, решить
позже. «Позже» оставляет режим `dirty`, а не выбрасывает правку.

Тихий last-write-wins выбросил бы работу другого устройства без следа за пределами
истории git — для личной базы знаний это хуже секундного трения.

Диалог подключается через `setConflictResolver`; мост к React — в
`src/components/sync/ConflictHost.tsx`. Конфликты выстраиваются в очередь, а не
теряются: слив может наткнуться на несколько подряд.

### Pull

`listDir(modesDir)` → по каждому `.md`: `getContent` → parse → сравнение `updatedAt`.
Новее в репозитории — забираем; новее локально — только обновляем `sha`.

**Локальные записи, чей файл в репозитории пропал, не удаляются.** Считаются как
`localOnly` и показываются числом. Автоудаление по одному листингу — который мог быть
неполным — это способ потерять весь архив. Следующий push файлы восстановит.

Испорченный файл сообщается по-файлово (`report.errors`), а не обрывает pull.

## Отчёт

`SyncReport`: `pushed`, `pulled`, `deleted`, `localOnly`, `conflictsPending`,
`errors`. Показывается тостом; счётчик неотправленного всегда виден строкой под
списком, чтобы ничего не оставалось *молча* несинхронизированным.

## Настройка второго репозитория

Всё настраиваемое: `owner`, `repo`, `branch`, папка записей, папка картинок. Можно
указать существующий Obsidian-vault со своей структурой — pull читает только папку
записей и не трогает посторонние файлы. Инструкция для пользователя — в
`docs/setup.md`.
